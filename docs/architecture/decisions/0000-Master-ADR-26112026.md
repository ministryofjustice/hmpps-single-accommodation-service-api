
# ADR – Shared Rules Engine and Eligibility Rules Graph (As-Is)

## Context

The Single Accommodation Service (SAS) API implements a shared Rules Engine to evaluate eligibility, service requirements and application lifecycle statuses across: Community Accommodation Service Tier 1 – Approved Premises, Community Accommodation Service Tier 2 – Short-term Accommodation, Community Accommodation Service Tier 3 – Temporary Accommodation, Duty to Refer(DTR),Commissioned Rehabilitative Services(CRS), Proposed Accommodation(PA), Public Protection Checker(PPC)

Each service or intervention has a dedicated decision tree that reflects its business requirements while reusing a common architectural framework for rule execution, context management and decision outcomes.

## Architectural decisions

- **Shared Rules Engine** – A common Rules Engine is implemented within the SAS API Query module, supporting all seven decision trees.
- **Embedded architecture** – The Rules Engine is implemented in Kotlin using Spring components rather than a separately deployed rules execution platform.
- **Service-specific decision trees** – CAS1, CAS2, DTR etc each have a dedicated `EligibilityTreeProvider` implementation.
- **Declarative decision modelling** – Decision trees are constructed using a shared `DecisionTreeBuilder`, defining rules, transitions and outcomes explicitly.
- **Separation of concerns** – Business rules, rule execution, decision tree construction, context management and outcome transformation are separated.
- **Reusable business rules** – Common business conditions can be reused across multiple decision trees, whilst service-specific rules remain independently defined.
- **Rule composition** – Individual business conditions are grouped into rule sets that produce a PASS or FAIL result.
- **Explicit rule precedence** – The structure of each decision tree determines the order of rule evaluation and the precedence of business outcomes.
- **Conditional branching** – Decision nodes determine subsequent evaluation pathways based on rule set outcomes.
- **Context-driven evaluation** – A common `EvaluationContext` carries domain data and intermediate decision results throughout evaluation.
- **Context transformation** – Dedicated context updaters modify evaluation results on successful or unsuccessful rule evaluation.
- **Standardised decision outcomes** – Decision trees return a common `ServiceResult` model, representing service-specific statuses and associated information.
- **Decision explainability** – Rule failure reasons can be propagated into applicable decision outcomes.
- **Cross-service dependencies** – Decision trees can consider the status of other services and interventions when determining eligibility or required actions.
- **Code-based rule management** – Business decision logic is defined and version-controlled within the application codebase.
- **Rules Graph separation** – The graphical tooling uses a dedicated Spring profile while reusing the underlying Rules Engine configuration.

## Service coverage

All seven decision tree implementations have been reviewed directly against the Kotlin source code.

| Service | Decision tree responsibility |
| --- | --- |
| **CAS1 – Approved Premises** | Eligibility, applications, placement requests, placement status and the 28-week timeframe. |
| **CAS2 – Short-term accommodation (ISR)** | Eligibility, applications, assessments, offers, arrival status and the 15-day timeframe. |
| **CAS3 – Temporary accommodation** | Eligibility, referrals, assessments, bookings, DTR/CRS dependencies and the 15-day timeframe. |
| **DTR – Duty to Refer** | Referral requirements, existing referral status, next accommodation and the 8-week timeframe. |
| **CRS – Commissioned Rehabilitative Services** | Live referrals, settled accommodation, next accommodation and the 12-week timeframe. |
| **PA – Proposed Accommodation** | Next accommodation status and dependencies on active CAS1 or CAS3 applications. |
| **PPC – Public Protection Checker** | Whether a check is required, completion status and public protection requirements. |

## Common business decision patterns

The source code also demonstrates the following architectural patterns across the seven decision trees:

- **Existing activity precedence** – Existing applications, referrals, placements, bookings or completed checks can take precedence over new eligibility assessments.
- **Conditional timeframe evaluation** – Timeframe restrictions are applied at specific points within individual decision trees rather than through a universal upfront check.
- **Distinction between outcomes** – The engine supports not eligible, not required, not started, upcoming, in-progress and completed outcomes, where applicable.
- **Domain-specific dependencies** – Individual decision trees evaluate relevant accommodation, risk, referral and application information.
- **Extensibility** – Additional decision trees can be introduced through the existing `EligibilityTreeProvider` interface and shared engine components.

## Consequences

- Consistent architectural implementation across all seven decision trees.
- Reduced duplication of common rule execution logic.
- Independent management of service-specific business requirements.
- Explicit and traceable decision pathways.
- Changes to shared rules may impact multiple decision trees.
- Changes to rule sequencing can alter business outcomes.
- Business rule changes are managed through application code changes.
